        <h2>Git Fork</h2>
        <p>
            Git Fork is the process of creating a copy of another developer's repository in your own account.
            By forking, you can make changes to a project freely without affecting the original repository.
            This is an essential feature for contributing to open-source projects and collaborative development within organizations.
        </p>
        <p>
            After making changes to a forked repository, you can propose those changes to the original repository
            by creating a Pull Request (or Merge Request). This allows the project maintainers to review your changes
            and merge them into the original repository if appropriate.
        </p>

        <div class="category-description">
            <h3>Basic Concepts of Forking</h3>
            
            <h4>Difference Between Fork and Clone</h4>
            <p>
                In Git terminology, "fork" and "clone" are similar but distinct concepts:
            </p>
            <ul>
                <li><strong>Fork</strong>: A server-side operation that creates a copy of another user's repository in your account.
                Forking is primarily a feature of Git hosting services like GitHub and GitLab.</li>
                <li><strong>Clone</strong>: An operation that creates a copy of a remote repository on your local machine.
                This is done using the <code>git clone</code> command.</li>
            </ul>
            <p>
                In a typical workflow, you first fork a repository and then clone your fork to work on it locally.
            </p>
            
            <h4>Main Uses of Forks</h4>
            <p>
                Forks are primarily used for the following purposes:
            </p>
            <ul>
                <li>Contributing to open-source projects</li>
                <li>Starting new projects based on existing ones</li>
                <li>Collaborative development within organizations (especially when access permissions are restricted)</li>
                <li>Developing experimental changes or features</li>
            </ul>
        </div>

        <div class="category-description">
            <h3>How to Fork Repositories</h3>
            
            <h4>Forking on GitHub</h4>
            <p>
                The process of forking a repository on GitHub is very simple:
            </p>
            <ol>
                <li>Navigate to the repository page you want to fork.</li>
                <li>Click the "Fork" button in the top-right corner of the page.</li>
                <li>Select the destination organization if needed.</li>
                <li>Click the "Create fork" button.</li>
            </ol>
            <p>
                Once the fork is complete, a copy of the original repository will be created in your account.
                The URL of this repository will typically be <code>https://github.com/your-username/repository-name</code>.
            </p>
            
            <h4>Forking on GitLab</h4>
            <p>
                The process for forking a repository on GitLab is similar:
            </p>
            <ol>
                <li>Navigate to the project page you want to fork.</li>
                <li>Click the "Fork" button in the top-right corner of the page.</li>
                <li>Select the namespace (user or group) where you want to fork the project.</li>
                <li>Modify the project name and other settings if needed.</li>
                <li>Click the "Fork project" button.</li>
            </ol>
        </div>

        <div class="category-description">
            <h3>Working with Forked Repositories</h3>
            
            <h4>Cloning Your Fork and Setting Up Remotes</h4>
            <p>
                To work with your forked repository locally, first create a clone:
            </p>
            <pre><code>git clone https://github.com/your-username/repository-name.git
cd repository-name</code></pre>
            <p>
                To make it easier to sync with the original repository (upstream repository), it's recommended to add an "upstream" remote:
            </p>
            <pre><code>git remote add upstream https://github.com/original-owner/repository-name.git</code></pre>
            <p>
                To verify that the remotes are set up correctly:
            </p>
            <pre><code>git remote -v</code></pre>
            <p>
                This should display something like:
            </p>
            <pre><code>origin    https://github.com/your-username/repository-name.git (fetch)
origin    https://github.com/your-username/repository-name.git (push)
upstream  https://github.com/original-owner/repository-name.git (fetch)
upstream  https://github.com/original-owner/repository-name.git (push)</code></pre>
            
            <h4>Syncing with the Upstream Repository</h4>
            <p>
                To incorporate changes from the original repository (upstream repository) into your fork, follow these steps:
            </p>
            <pre><code># Fetch the latest changes from the upstream repository
git fetch upstream

# Switch to your local main branch
git checkout main

# Merge the changes from the upstream repository into your local main branch
git merge upstream/main

# Push the changes to your fork
git push origin main</code></pre>
            <p>
                This keeps your fork synchronized with the original repository and up to date.
            </p>
            
            <h4>Creating and Proposing Changes</h4>
            <p>
                The typical workflow for making changes in a forked repository and proposing them to the original repository is:
            </p>
            <ol>
                <li>Sync your fork with the upstream repository.</li>
                <li>Create a new feature branch:<br>
                <code>git checkout -b feature/new-feature-name</code></li>
                <li>Make changes and commit them:<br>
                <code>git add .</code><br>
                <code>git commit -m "Description of changes"</code></li>
                <li>Push the changes to your fork:<br>
                <code>git push origin feature/new-feature-name</code></li>
                <li>Create a pull request (or merge request) to the original repository using the GitHub or GitLab web interface.</li>
            </ol>
        </div>

        <div class="category-description">
            <h3>Creating and Managing Pull Requests</h3>
            
            <h4>Creating a Pull Request on GitHub</h4>
            <p>
                The steps to create a pull request on GitHub are:
            </p>
            <ol>
                <li>Navigate to your forked repository page.</li>
                <li>Click the "Pull requests" tab.</li>
                <li>Click the "New pull request" button.</li>
                <li>Select the base repository (original repository) and branch, and the compare repository (your fork) and branch.</li>
                <li>Review the changes and click the "Create pull request" button.</li>
                <li>Enter a title and description for your pull request.</li>
                <li>Click the "Create pull request" button to finalize.</li>
            </ol>
            
            <h4>Pull Request Best Practices</h4>
            <p>
                Best practices for creating effective pull requests include:
            </p>
            <ul>
                <li><strong>Clear title and description</strong>: Concisely explain what changes you've made and why they're necessary.</li>
                <li><strong>Break down large changes</strong>: Divide large changes into multiple smaller pull requests to make review easier.</li>
                <li><strong>Add tests</strong>: When possible, include tests for your changes.</li>
                <li><strong>Follow coding conventions</strong>: Adhere to the project's coding conventions and style guides.</li>
                <li><strong>Respond to review comments</strong>: Respond promptly and courteously to feedback from reviewers.</li>
            </ul>
            
            <h4>Making Changes After a Pull Request</h4>
            <p>
                If additional changes are needed after submitting a pull request, simply commit and push to the same branch:
            </p>
            <pre><code>git add .
git commit -m "Address review feedback"
git push origin feature/new-feature-name</code></pre>
            <p>
                These changes will automatically be added to the existing pull request.
            </p>
        </div>

        <div class="category-description">
            <h3>Managing and Maintaining Forks</h3>
            
            <h4>Regular Synchronization with Upstream</h4>
            <p>
                When using a fork over an extended period, it's important to synchronize regularly with the upstream repository.
                This minimizes conflicts and allows you to incorporate the latest features and bug fixes.
            </p>
            <p>
                The frequency of synchronization depends on how active the upstream repository is, but it's recommended
                to always sync before making new changes.
            </p>
            
            <h4>Handling Forks That Are No Longer Needed</h4>
            <p>
                When you've completed your contributions to a project and no longer need the fork, you have several options:
            </p>
            <ul>
                <li><strong>Keep it</strong>: You can retain the fork if you might contribute again in the future.</li>
                <li><strong>Archive it</strong>: On GitHub and GitLab, you can archive a repository to make it read-only.</li>
                <li><strong>Delete it</strong>: If completely unnecessary, you can delete the fork. Note that this action cannot be undone.</li>
            </ul>
        </div>

        <div class="category-description">
            <h3>Advanced Usage of Forks</h3>
            
            <h4>Contributing to Other Forks</h4>
            <p>
                It's also possible to contribute to someone else's fork. This is useful when multiple developers
                are collaborating to propose a significant change to the original repository.
            </p>
            <p>
                In this case, you can add their fork as a remote and pull from or push to it:
            </p>
            <pre><code>git remote add collaborator https://github.com/collaborator-username/repository-name.git
git fetch collaborator
git checkout -b feature/collaborative-feature collaborator/feature/collaborative-feature
# Make changes
git push collaborator feature/collaborative-feature</code></pre>
            
            <h4>Using Forks for Experimentation</h4>
            <p>
                Forks are ideal for trying experimental changes without affecting the original project.
                For example, you can test new technologies or approaches, or perform large-scale refactoring.
            </p>
            <p>
                If the experiment is successful, you can propose the changes to the original repository.
                If it fails, there's no impact on the original project.
            </p>
        </div>

        <div class="category-description">
            <h3>Common Problems and Solutions</h3>
            
            <h4>Resolving Merge Conflicts</h4>
            <p>
                Merge conflicts can occur when syncing with the upstream repository or when creating a pull request.
                This happens when the same part of a file has been changed in different ways.
            </p>
            <p>
                To resolve merge conflicts:
            </p>
            <ol>
                <li>Open the files with conflicts.</li>
                <li>Look for conflict markers (<code>&lt;&lt;&lt;&lt;&lt;&lt;&lt;</code>, <code>=======</code>, <code>&gt;&gt;&gt;&gt;&gt;&gt;&gt;</code>).</li>
                <li>Edit the code appropriately to integrate both changes or choose one over the other.</li>
                <li>Remove the conflict markers.</li>
                <li>Stage and commit the changes:<br>
                <code>git add .</code><br>
                <code>git commit -m "Resolve merge conflicts"</code></li>
            </ol>
            
            <h4>When a Fork Becomes Outdated</h4>
            <p>
                Forks that haven't been synchronized for a long time can fall significantly behind the upstream repository.
                In this case, you can:
            </p>
            <ul>
                <li><strong>Rebase</strong>: Rebase your changes on top of the upstream changes.<br>
                <code>git fetch upstream</code><br>
                <code>git rebase upstream/main</code></li>
                <li><strong>Re-create the fork</strong>: In extreme cases, it might be easier to delete the fork and create a new one.</li>
            </ul>
        </div>

        <div class="category-description">
            <h3>Summary</h3>
            <p>
                Git Fork is an essential feature for contributing to open-source projects and collaborative development.
                By using forks, you can contribute to projects even without direct access to the original repository,
                or start new projects based on existing code.
            </p>
            <p>
                Effective use of forks involves regular synchronization with the upstream repository, proper branch management,
                and creating clear pull requests. By following these practices, you can enable smooth collaborative development
                and effectively contribute to open-source communities and team development.
            </p>
            <p>
                Forking is not just a technical feature but also a social tool that enables distributed collaborative development.
                It allows developers from around the world to collaborate beyond geographical constraints and create better software together.
            </p>
        </div>
